AETHONE — RELRO-16KB two-case analysis, RAW DATA (bundle v3, 2026-10-31)
======================================================================
Method: readelf -lW on the REAL official Aether v2.4.0 release binaries
(sha256-verified downloads; see elf_inspection_log.txt). The two-case rule
is quoted verbatim from developer.android.com/guide/practices/page-sizes
in android_pagesizes_doc_excerpt.txt.

THE RULE (official doc, verbatim):
  "The modulo formula applies when GNU_RELRO shares a LOAD segment with
   subsequent writable data (such as .data or .bss)."
  Own-LOAD case: "Because the entire LOAD segment contains only RELRO data,
  there's no writable data in the sub-range ... Additionally, any subsequent
  writable LOAD segment begins on a separate 16 KB page boundary ... The
  linker's read-only protection won't overlap with any writable data, so no
  segmentation fault occurs."
  Crash mechanism (official doc example): the linker mprotects
  [page_down(relro_vaddr), page_up(relro_vaddr+memsz)) read-only; any
  WRITABLE byte inside that range causes a segfault at runtime.

CONCLUSION (v3, corrects the v2 verdict):
  * aether ARM64 : own-LOAD placement; next RW LOAD 0x1225f80 starts at/after
    0x1224000 = page_up(relro_end). No writable byte inside the mprotect
    range. kb16_relro = PASS. The v2 'FAIL' (remainder 8192) was a FALSE
    POSITIVE caused by applying the formula unconditionally.
  * aether x86_64: own-LOAD placement; next RW LOAD 0x1412ad0 starts at/after
    0x1410000 = page_up(relro_end). kb16_relro = PASS. The v2 'FAIL'
    (remainder 12288) was likewise a FALSE POSITIVE.
  * aether armv7 : 4KB architecture -> 16KB rule N/A (data recorded above).
  * The psiphon-tunnel-core and lyrebird Go executables have NO PT_GNU_RELRO
    segment at all (static EXEC) -> no RELRO requirement (trivially compliant).
  * Runtime in a real 16KB Android environment: NOT TESTED (static analysis
    only — no emulator/device run has been performed).
