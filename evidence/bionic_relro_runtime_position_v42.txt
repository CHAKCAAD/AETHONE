2. WHAT IS DOCUMENTED INSTEAD — the real, source-documented risks
---------------------------------------------------------------------------
The runtime risk with multiple RELRO segments is NOT "unsupported", it is
the documented OVER-PROTECTION / OVERLAP hazard of each segment's
page-rounded protection range:

R1. Page-boundary over-protection (single or multiple segments).
    The linker rounds every RELRO segment's protection range outwards to
    whole pages: seg_page_start = page_start(p_vaddr), seg_page_end =
    page_end(p_vaddr + p_memsz) (EXCERPT 3). The in-source comment states
    this is deliberately "over-protective" and, quoting Ian Lance Taylor's
    description (reproduced in the source): "If there is anything on the
    page which should not be read-only, the program is likely to fail at
    runtime." With MULTIPLE RELRO segments this hazard repeats INDEPENDENTLY
    PER SEGMENT: each additional segment adds its own rounded start/end
    pages, so the total region forced read-only can only grow. A protection
    range that overlaps any page containing data that must remain writable
    => likely segmentation fault at first write to that page.

R2. Shared-LOAD placement rule (official 16 KB documentation).
    developer.android.com/guide/practices/page-sizes (Last updated
    2026-10-16 UTC, EXCERPT 4): a RELRO section whose (VirtAddr + MemSiz) is
    not 16 KB aligned "crashes the app at runtime with a segmentation fault"
    — the protection range turns read-only a sub-range the linker expects
    writable. The rule applies when GNU_RELRO shares its LOAD segment with
    subsequent writable data; when RELRO is in its own LOAD (no writable
    data in the sub-range, next writable LOAD on a separate page) the file
    is compliant even with a non-zero remainder. Both official artifacts'
    verdicts (arm64, x86_64: own-LOAD => PASS) are unchanged.

R3. 16 KiB app-compat extension path hazards (bionic source, EXCERPT 2).
    `_extend_gnu_relro_prot_end` documents the hazard of "incorrect write
    protection of non-relocation data" if page-aligned memsz were used, and
    when relro_memsz < containing-load memsz it ABANDONS the extension
    entirely (`return;`), leaving a separate (split) VMA instead of extending
    the protection. This path additionally only activates on a 16 KiB kernel
    for ELFs with min p_align 4096 when `bionic.linker.16kb.app_compat.enabled`
    is on — a temporary condition per the in-source comment ("removed once
    app compat is made the default on 16KiB devices").
