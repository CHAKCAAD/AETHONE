## 2. Firefox over Warp — the engine side (contract 1.4.0-warp)

The engine gained two ADDITIVE, OPTIONAL config seams (`docs/FIREFOX_VPN_ENGINE.md`
§3):

| Field | Meaning |
|---|---|
| `apiProxy` | `socks5://host:port` — route the CONTROL plane (FxA / Guardian / RemoteSettings) through the carrier. **The uTLS Firefox ClientHello survives the chaining** (the chaining upgrade over the upstream's own `-api-proxy`, which drops to Go's ClientHello + HTTP/1.1 — the exact blacklisted signature per the upstream's OPERATOR.md). |
| `upstreamProxy` | `socks5://host:port` — dial the h2 MASQUE data plane through the carrier. |

Contract gates (all tested):

* `socks5`/`socks5h` with an explicit `host:port` only —
  `apiProxyInvalid` / `upstreamProxyInvalid` otherwise;
* `h3` + `upstreamProxy` is REFUSED (`transportUnsupportedOverProxy`) —
  QUIC/UDP cannot ride a TCP SOCKS CONNECT carrier (the aether
  listener's UDP ASSOCIATE carries DNS, nothing else);
* a host that sends neither URL keeps the byte-equivalent direct
  behavior (the `NewH2ProxySession` path is unchanged;
  `TestH2SessionCarrierDirectEquivalence` pins that).

New `internal/carrier` package (NEW AETHONE code — provenance recorded
in `phase1/fxv/ORIGIN.md`): the SOCKS5 client dialer follows the pinned
upstream's own `-api-proxy` client (`golang.org/x/net/proxy`, remote
DNS — the hostname crosses the carrier, the engine never resolves
control-plane names locally), and `NewControlPlaneTransport` wraps it
with the uTLS Firefox preset mirrored from the upstream's
`dialFirefoxTLS`.

Test evidence (all green, `go test ./...`):

* `internal/carrier` — URL shape; a full roundtrip through the fxv SOCKS
  server; the Firefox ClientHello captured THROUGH the carrier and
  fingerprint-checked with the upstream's own cipher-suite assertion
  (first suite `0x1301`, legacy `0x0035`/`0x009c` present, ≥15 suites);
* `internal/upstream` — **a complete h2 MASQUE session built through the
  carrier** (TLS + CONNECT tunnel + payload roundtrip through a fake
  h2 CONNECT proxy behind the SOCKS server). Building this surfaced a
  genuine test-server lesson: an h2 CONNECT proxy handler MUST flush
  after every response write — the responseWriter buffers DATA frames
  and the tunnel otherwise deadlocks on its first chunk (the fix is in
  the test's `copyWithFlush`, documented for future harnesses);
* `cmd/libfirefoxvpn` — end-to-end: with `apiProxy` set, the engine's
  first control-plane request arrives at the carrier carrying the
  mozilla hostname (remote-DNS intact) and the refused dial fails the
  walk honestly; the two config gates above.

## 3. Firefox over Warp — the app side

`_connectFirefox` now walks the chain order (mirroring
`psiphonChain`):

```
permission → zeptun TUN (1822, tcpOnly) → [NEW] the WARP carrier leg
(the in-process aether core, protocol = CoreSettings.firefoxLegProtocol,
listener 1819 waited for AND probed end-to-end — «ابتدا به وارپ متصل
بشه و بعد فایرفاکس») → the engine child (SOCKS5 1822, apiProxy +
upstreamProxy = socks5://127.0.0.1:1819, transport h2) → socksReady →
the end-to-end probe through 1822 → Connected.
```

* The warp leg is NEVER country-pinned — the exit country stays the
  Firefox pick (the wheel/`--discover` model is untouched).
* `_jobId`/`_core` now live for the firefox walk, so `_hardCleanup`,
  the process-side job registry, and the steady-state health ticker
  (core liveness) all cover the carrier leg exactly like a plain WARP
  session.
* The honest Windows limit is LIFTED: the engine no longer dials the
  internet directly at all (loopback carrier only), and the in-process
  core rides the plain-WARP path that already tunnels on every desktop.
* The transport is h2, full stop. The old h2/h3 picker on the Firefox
  settings page is replaced by an honest note (H3/QUIC cannot ride the
  TCP carrier) — offering a dead option would be a lie. The store field
  stays (`h2` default).

### The core-protocol picker (decree 3)

The Firefox settings page carries the same per-family leg picker the
tor and psiphon pages have (`AetherLegProtocol`: WireGuard / MASQUE /
GOOL / GOOL Classic / MIM → `CoreSettings.firefoxLegProtocol`,
default WireGuard, legacy `aetherLegProtocol` blobs migrate into it).
Strings added for all five locales (fa/en/ru/zh/tk).

## 4. The tunnel-apps picker (decree 4)

**Root cause of the missing apps**: the Kotlin `installedApps()`
queries `ACTION_MAIN`/`CATEGORY_LAUNCHER` — but on Android 11+
package-visibility filtering applies to `queryIntentActivities` too, so
without a `<queries>` declaration the picker only ever saw a small
automatic-visibility subset of the launchable apps. The manifest now
declares the launcher intent (the documented launcher/app-picker
pattern — no `QUERY_ALL_PACKAGES`, which is Play-restricted).

**Section order**: the per-app tunneling section moved to the END of
the routing page (after the expert routes section), per the decree. The
row label's hardcoded `textDirection.rtl` became
`Directionality.of(context)` — Latin app names no longer get mirrored
ellipsis placement in the LTR locales (a Turkmen-visible wart).

## 5. The Turkmen language (decree 5)

**Root cause**: `AethoneApp._locale('tk')` deliberately mapped the
Turkmen pick onto `Locale('en')` (the v4.41 comment assumed
`AppStrings` would still resolve tk — but `AppStrings.of` reads the
MATERIAL locale, saw `en`, and rendered the English table forever; the
complete v4.41 tk table was dead code).

**Fix**: `tk` is now a first-class locale — `supportedLocales` carries
`Locale('tk')`, `_locale('tk')` maps to itself, and three tiny fallback
delegates (`app.dart`) claim exactly the tk locale and load the English
Global\* resources for the framework widgets (flutter_localizations
ships no tk). Regression tests (`test/turkmen_locale_test.dart`) pump
the REAL shell with the tk pick and assert the Turkmen strings render
(and that the Material/Widgets/Cupertino localizations exist under tk).
