# Relay system — design and mission report (2026-11-12)

Branch: `feature/firefox-vpn-relay` (from `update/firefox-vpn-core` @
`863fdca`). Owner order of 2026-11-12: lift the Guardian authorization
sanction (HTTP 451 `unavailable_in_region`, observed from Iran) by
modeling the relay system of `armanlife/firefox-vpn-client` /
`armanlife/arman-vpn-client` v1.0.17 — Guardian-focused, but allowed to
cover the other control-plane services. Full user guide:
`docs/firefox-vpn/relay.md`. Provenance: `phase1/fxv/ORIGIN.md` § relay.

## 1. The problem

Mozilla's CDN edge refuses some regions at the Guardian control plane
(`vpn.mozilla.org`) with HTTP 451: the account is fine, the Fastly
MASQUE tunnels are fine, but the ProxyPass authorization cannot be
fetched — so the engine can never connect. The 451 is issued at the
edge for the literal Guardian path, BEFORE the origin.

## 2. The reference system (what Arman v1.0.17 does)

* **Region recovery hook** in the Guardian client: on 451, first retry
  the SAME request with a doubled leading slash (`//api/v1/fpn/...`) —
  the edge rule does not match the doubled form, the origin routes it
  to the same handler. Free, no third party.
* **Shared relay pool** (the v1.0.17 headline): after a 451 survives
  the doubled path, a LAZY pool of community relays (the public
  arman-org update manifest, 10-minute cache, health-probed,
  shuffled, one 20s-budget walk) carries Guardian `/api/v1/fpn/*`
  requests only. VPN traffic never relays.
* **Personal relay** (all control-plane hosts): the user's own
  https relay URL (a Cloudflare Worker or PHP file). Direct first;
  on unreachability (nothing sent — a GotConn-traced proof) or 451,
  through the relay; then relay-FIRST for 10 minutes.
* **The wire protocol**: `https://RELAY/?secret=S&url=TARGET` —
  method/headers/body forwarded, response returned; refusals set
  `X-Relay-Error`; a genuinely forwarded response carries
  `X-Arman-Relay: 1`; `?health=1` answers
  `{"relay":"arman-vpn","version":1,"ready":true}`.
* **Leg hardening**: TLS 1.2 fallback and (for workers.dev relays) an
  edge route that connects via a reachable Cloudflare name while SNI
  and HTTP Host keep naming the relay; optional ECH (off/on/require).

## 3. What AETHONE implements (original code, same protocol)

`phase1/fxv/internal/relay/` — four files, ~1,300 lines with tests:

| File | Role |
|---|---|
| `relay.go` | `Options` + `Install` (the `vpnclient.SetControlPlaneTransport` seam — the pinned upstream is NEVER modified), the `stack` decision walk, the doubled-path builder, the `relayTransport` wire protocol, the double-delivery guards |
| `shared.go` | The lazy community pool: manifest load (filter/dedup/cap, disabled-is-authoritative, mirror fallback, failed-refresh keeps the list), the health probe (accepts BOTH community identities `arman-vpn` and `aethone`), the recovery walk (bad-for-a-minute skipping, sticky active relay, non-idempotent STOP) |
| `leg.go` | The per-relay connection leg: primary / TLS 1.2 / workers.dev edge routes, the preferred-route memory, the soft deadline (only while routes remain), the retryable-error set |
| `ech.go` | ECH (off/on/require), the DoH HTTPS-record key lookup (JSON form, clamped TTL, negative-answer caching), the stale-key retry, the fail-closed require mode |

Layer order (cheapest first): **doubled path → shared pool (Guardian
FPN only) → personal relay (any control-plane host) → relay-first
window (10 min)**. Double-delivery safety: a request is re-sent ONLY
when the connection provably never opened (the httptrace GotConn hook
never fired) or the answer was a closed 451, AND the body is
replayable; everything else surfaces its error as-is.

## 4. The engine contract (1.3.0-relay, additive)

`engine.Config` (tunnel) and `engine.LoginConfig` (login) both gain an
OPTIONAL `relay` object: `personal_url`, `personal_enabled`,
`shared_enabled`, `ech_mode`, `ech_config`. Detail codes
`relayURLInvalid` / `relayECHModeUnknown` / `relayECHConfigInvalid`
(fail-fast shape validation — a stored-but-disabled URL is validated
too). A host that sends no `relay` keeps the exact 1.2.0 behavior; the
doubled-path bypass needs no configuration at all. Older engines
ignore the new field (plain `json.Unmarshal`); newer engines treat its
absence as the zero value.

`runTunnel` installs the stack BEFORE the first control-plane request
(the server-list fetch); `runLogin` installs it before the FxA exchange
(the personal layer covers FxA unreachability; the Guardian-scoped
layers stay dormant during a login).

## 5. The app surface

* `FirefoxRelaySettings` (firefox_protocol.dart) rides BOTH the tunnel
  and the login config lines; `EngineConfigSource` gains five relay
  getters with concrete defaults (test fakes untouched), the store
  persists them (`settings_persistence.dart`), and the Firefox
  settings page gains a «سرور رله» section: the shared-pool switch
  (ON by default — the v1.0.17 posture), the personal-relay switch +
  URL field, and the ECH mode pills (خودکار / خاموش / اجباری) —
  5-locale strings (fa/en/ru/zh/tk).
* The URL field commits through `setFirefoxRelayPersonalUrl` (trim);
  the address stays stored while the switch is off.

## 6. The reference servers (docs/firefox-vpn/relay/)

`worker.js` (Cloudflare Worker) and `relay.php` — ORIGINAL
implementations of the community protocol with AETHONE branding: the
secret gate, the browser status page, the local `?health=1` answer
(`{"relay":"aethone","version":1,"ready":true}`), the host allowlist
(mozilla/mozilla.com/firefox/github/githubusercontent/jsdelivr),
hop-header and `cf-*` stripping, the `X-Aethone-Relay: 1` forwarded
marker and the `X-Relay-Error` refusal channel. Interchangeable with
any endpoint built from the same spec.

## 7. Honest deltas vs. the reference

1. The reference bounds the first direct attempt with a 4s quick dial;
   the pinned upstream exports no dial-injection seam, so AETHONE
   keeps the upstream's own dial budget — the first blocked request
   may wait that budget once, then the 10-minute window amortizes.
2. The reference resets relay state on network-change events; AETHONE
   relies on the window's expiry plus the relay-failure→direct retry
   (a network change shows up as a relay connect failure).
3. AETHONE's shared pool accepts BOTH health identities (`arman-vpn`,
   `aethone`) — relays deployed from either guide serve either client.
